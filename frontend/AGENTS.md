## Critical lines

- Go-specific rules (testing framework, hexagonal layout, gofmt) do **not** apply here — only the shared workflow/commit/docs/behavior rules above.
- `bindings/` is **generated** from Go services by the Wails tooling (module is still `changeme`, so bindings live under `bindings/changeme/`). Never hand-edit; call bound methods via `@wailsio/runtime` instead.
- `tools/oxlint/anti-slop/` is a custom oxlint plugin wired up in `vite.config.ts` — treat its rules as enforced coding standards, and keep the plugin sources excluded from typecheck/lint as configured.
- Before finishing a change: `vp check` and `vp test` (see checklist below). Build from the repo root with `task build`; `npm run build` runs `tsc` + `vp build` for the frontend only.

## The chat surface (assistant-ui)

The chat view renders on the **assistant-ui runtime**: the store stays the single source of truth and a thin
external-store adapter exposes it to the primitives. Never hand-roll a transcript, tool card or composer
element that the vendored set already covers.

```
src/features/chat/
├── runtime/        the adapter: mapping.ts (entries → messages), branches.ts (variants),
│                   useChatRuntime.ts (store selectors/actions only), ChatRuntimeProvider.tsx
├── thread/         the transcript: ChatThread, ChatAssistantMessage, ChatUserMessage,
│                   DayDivider, ConversationMapRail, TurnActivity
├── tools/aui/      the tool layer: renderers.tsx (name → renderer), ToolCallFrame,
│                   ChatToolGroup (the heavy-turn fold), markers.ts, diffRows.ts
├── run/            the run surfaces (the plan + subagent lanes) — anchored to the
│                   thread viewport's relative wrapper, never over the composer
└── composer/       the composer: ChatComposer, composerTriggers, ComposerPickers,
                    ComposerContext
```

`src/components/assistant-ui/` is **vendored** (generated by `npx assistant-ui@latest add …`): the element set
plus the shadcn primitives it needs under `ui/`. It is never hand-edited — the vendored tree is exempt from
`vp check`, and buddies behaviour lives in the wrappers under `features/chat/`. The one sanctioned exception is
`elements/surfaces.tsx`, the shared retheming seam.

**The transcript is one flat reading surface** (change `flatten-chat-transcript`): the reasoning is a muted
disclosure line, a tool call is a quiet line with no card surface (the name recedes, the sentence carries the
payload, the body opens under a hairline rail), a run of fewer than four calls renders inline in the flow, and
every assistant turn opens with a rule. The answer and the rows above it share one left edge and one measure.
That look rides the vendored elements' own `variant` and `className` props — never a vendored edit.

**Re-vendoring** (the recipe, the exact commands and every installed version):
[`src/components/assistant-ui/VENDORED.md`](src/components/assistant-ui/VENDORED.md). Re-vendor with `add -o`,
re-apply the `surfaces.tsx` retarget, then re-run the suite — the VENDORED.md file records the divergences that
have to be re-applied by hand.

**The rules that bite:**
- The runtime adapter holds **no state of its own**: derive from the store, mutate only through store actions.
- A message's id is the turn id and a part's id is the entry id — component state survives reorders.
- The streaming text path still renders through `react-markdown` (the vendored `MarkdownText` hardcodes `defer`,
  so it renders nothing while a part streams) and must keep the `remark-gfm` plugin: without it a streaming
  table renders as pipe text.
- Every new file goes through `vp check --fix` before it lands; the anti-slop rules are enforced.

# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management, and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Built-in Commands vs Scripts

`vp <name>` runs a built-in command. `vp run <name>` runs a `package.json` script or a `vite.config.ts` task. Scripts cannot overwrite built-ins, so `vp dev` and `vp run dev` may do different things. Check `package.json` and `vite.config.ts` first, and run `vp run <name>` when the project defines a script or task with that name.

## Tool Versions

Run `vp toolchain` to show versions and relationships in the active Vite+
release. Add a tool name to select part of the graph. For example, run
`vp toolchain vite`. Use `--global` to ignore the local `vite-plus` package. Use
`vp why <package>` to show the package-manager dependency graph.

## Review Checklist

- [ ] Run `vp install` after pulling remote changes and before getting started.
- [ ] Run `vp check` and `vp test` to format, lint, type check and test changes.
- [ ] Check if there are `vite.config.ts` tasks or `package.json` scripts necessary for validation, run via `vp run <script>`.
- [ ] If setup, runtime, or package-manager behavior looks wrong, run `vp env doctor` and include its output when asking for help.

# Design

## Context

The runtime port (change `port-agent-runtime`) left `runTurn` shaped as "phases 1–8 build the turn, phase 9 `turnAgent.Run` + `drainTurn`, phase 10 terminal": a `busy` map keyed by session with no handle, a `record` closure persisting on the live turn ctx (a `recordCtx` exists but is used only by background delegations), and no cancellation path (documented in `internal/agents/hooks.go`). Checkpoints already live in SQLite (`store.Checkpoints()` — structurally identical to eino's `CheckPointStore`), currently occupied by compaction state under `checkpoint_<sessionID>` keys. `Send(sessionID, text)` is stable across four layers, and every model knob needed (OpenAI reasoning effort, Claude thinking config, Gemini thinking config) exists unused in the pinned eino version. `ChatService.Transcript` does a full-log replay; the frontend folds it through one reducer with session-lifetime dedupe. See proposal.md for motivation; specs carry the behavior contract.

## Goals / Non-Goals

**Goals:**
- One resolution path for a turn's effective configuration (session override → agent default) consumed by model build, effort mapping, header/sidebar/pickers, and context accounting alike.
- Keep `Send(sessionID, text)` and the linear append-only event log as invariants; all new turn inputs ride existing rows or new event payloads — no schema reshape of `session_events`.
- Adopt `adk.Runner` exactly where checkpointed interrupt/resume requires it; keep the rest of `runTurn` untouched.
- Every migration additive and forward-compatible: an older binary reading the new database must still run (unknown event kinds are skipped by replay, new columns have defaults).

**Non-Goals:**
- Per-message agent/model routing within one transcript; cross-device session indexing; browser-mirror and members panel sources (no backing subsystems — see proposal out-of-scope).
- Plumbing `agent.Temperature` (pre-existing, unused — untouched here).
- Replacing the current store/reducer chat runtime with assistant-ui's runtime; the existing `applyEvent` reducer remains the single graph.

## Decisions

### D1: Overrides live on the session row; `Send` stays `Send(sessionID, text)`
`sessions.model` / `sessions.effort` (migration 000008, empty = inherit) are read in `manager.Send`, which already loads the session, and handed to `runTurn`. **Why:** zero signature churn across bindings/transport/store layers; overrides are durable and visible to context accounting; a session cannot disagree with itself turn-to-turn. **Alternatives:** per-send payload (rejected — drift within a session, changes 4 layers of signatures) and frontend-local preference only (rejected — invisible to the backend, lost on reinstall, contradicts the restart-survival scenarios).

### D2: Effort = a per-model capability set in the catalog, mapped to provider-native parameters
Extend `internal/agents/catalog.go` with effort options per model (canonical types, static table alongside context windows) and a heuristic resolver for openrouter-family models from the model id (`gpt-5*`/`o*` → OpenAI set, `claude-*` → thinking levels, `gemini-2.5*` → thinking levels; unknown → empty set ⇒ picker hidden). Normalized option sets (`low|medium|high`, optionally `minimal` where native) map per connector: openai → `acl/openai.WithReasoningEffort`; claude → `eino-ext claude.WithThinkingConfig` with thinking budget tiers (initial: low 4k / medium 16k / high 32k token budgets); gemini → `gemini.WithThinkingConfig` thinking-budget tiers (initial: low 512 / medium 2048 / high 8192 — replaceable with native thinking levels where the connector supports them). Unset means "don't set the parameter" (provider default), never a silent substitute. **Why:** one picker UX across providers while sending each provider's native knob; skips nonexistent capability metadata on live `/models` responses. **Alternative:** expose each provider's raw vocabulary in the UI (rejected — uneven UX and openrouter fetches carry no effort metadata at all). The `providerModels` binding returns `[]ModelCapability{ID, ContextWindow, Efforts}` — same DTO feeds both the config modal and the composer pickers. Budget tier numbers are tunable constants; changing them alters no spec.

### D3: Cancel = `adk.WithCancel()` safe points + 2s escalation to context cancel
Each run passes `adk.WithCancel()` and stores the `AgentCancelFunc` beside the busy flag (`map[sessionID]*runningTurn{cancel, adkCancel}`). Cancel invokes the ADK cancel (safe points: after model / after tool call), and a 2s escalation timer falls back to `context.CancelFunc`. Terminal recording switches `record`/`failTurn` to `recordCtx` (already exists) so the `turn_cancelled` event persists after the ctx dies. **Why:** mirrors onclaw's two-level cancel (safe points keep tool writes intact; escalation guarantees termination), and the `recordCtx` fix is required regardless. **Alternative:** plain ctx cancel only (rejected — kills in-flight tool execs mid-write and diverges from donor behavior).

### D4: Durable approvals = `Runner` swap, event-log pending state, one resume path
Phase 9 becomes `adk.NewRunner(RunnerConfig{Agent: turnAgent, EnableStreaming, CheckPointStore: store.Checkpoints()})` with `adk.WithCheckPointID("adk_" + turnID)` in non-session mode (no `SessionEventStore` — buddies keeps its own transcript). `drainTurn` gains one branch: `ev.Action.Interrupted != nil` → persist `approval_required` (payload: interrupt id, command, checkpoint id), exit *without* a terminal event and *without* clearing busy. The goroutine ends; the paused run is simply a busy session whose checkpoint is on disk.
Pending state derives from the event log (latest `approval_required` with no matching `approval_resolved`) — no schema change, replay-safe. `ResolveApproval(sessionID, interruptID, approved)` (a) validates against the derived pending set (stale ⇒ conflict), (b) records the decision in the checkpoint KV under `approval/<sha256(command)>`, consuming it on read, (c) calls `resumeTurn(sessionID, ...)`: if the process still holds the composed turn agent from the interrupted run, reuse it; after a restart, rebuild phases 4–9 (skip user-message persist and prompt gate — `ChatModelAgent.Resume` restores instruction/tool state from the checkpoint) and drive `Runner.Resume(ctx, checkpointID)`. Deny passes a denial result back as resume data so the tool reports the refusal to the model. The shell gate lives in `internal/agents/backend` `JailedShell.Execute`: safety-pattern match → resume-context check → ledger check → `tool.Interrupt(ctx, ShellApprovalInfo{Command})`, which the runtime already passes through untouched. Cancelling while pending cancels via `adkCancel` + appends `approval_resolved(cancelled)` and clears busy. **Why:** one resume path for live-pause and post-restart cases (in both, the original run loop has ended and resume is a fresh `Runner.Resume` from the stored checkpoint); pending-in-events avoids a waiting-state table. **Alternative:** in-time blocking hold channel (rejected — user chose durability), and storing pending state as a session column (rejected — event log already replays it to the transcript).

### D5: Attachments served through a bound service call, not an HTTP route
`attachments(key, name, mime, size)` table (migration `000009`) and files under `~/.buddies/attachments/<key>`; the frontend fetches content via a bound `AttachmentContent(key)` (media type + base64 payload, chunk parameters if large objects prove janky) and renders object URLs. The "capability URL" is therefore the unguessable key carried only by transcript events. **Why:** app-shell requires an identical service surface on both hosts; desktop has no HTTP file route, so a donor-style `/files/:key` would fork behavior between hosts — the binding works on desktop bridge and server mode unchanged (server mode's BearerGate already wraps every bound call). **Alternatives:** capability HTTP route (rejected — no desktop surface, splits the security model), base64 blobs inside event payloads (rejected — bloat every replay). Raw paths never reach the frontend; the reader and serving both key by capability id.

### D6: Transcript windowing = one new paged binding; reducer gains prepend
`TranscriptPage(sessionID, beforeSeq, limit)` returns the newest page initially (`limit ≈ 60`) and older pages on demand; `Transcript(sessionID)` remains for internal/compat callers. `selectSession` loads the newest page + subscribes (subscribe-before-load stays); "load earlier" folds an older page through the same `applyEvent` (ordered seq makes prepending idempotent against the dedupe set), and the transcript anchor uses the height-delta scroll fix. `runTurn`, `ContextUsage`, and compaction keep full-log reads — windowing only changes UI delivery. Boundary pages landing mid-turn merge in the reducer by `turn_id` (entries already key on it). **Why:** mechanical, matches the spec's observable behavior, no change to the event store. **Alternative:** full fetch with render-side slicing (rejected — moves the cost without fixing it and the spec's "until the beginning" implies real paging).

### D7: Branch variants = durable payload markers, grouped by one reducer
A regeneration is a real turn (new `turn_id`); its `user_message` payload carries `variant_of: <original turn id>` (the original text is not re-stored as a fresh prompt — the runner re-sends the original user text with a suppressed duplicate-persist flag), and its reply events group under the same marker. `applyEvent` builds a *slot* per original turn: variants array + active index (default newest when live, stored choice on replay via the last-marked variant). Failed regenerations drop the empty variant and restore the previous index. Variant navigation is pure local state; no fetch. **Why:** single linear log survives intact (data-store invariant), replay reconstructs the picker exactly (spec), and one reducer path serves live and replay. **Alternatives:** onclaw's client-only variants with localStorage persistence (rejected — dual truth diverges on reload, our spec requires replay parity); a normalized branches table (rejected — over-structure for five payload bytes).

### D8: Panels and run card derive entirely client-side; one jailed file-reader binding
Right-panel file/trajectory previews need a bound reader: `WorkspaceFile(agentID, relPath)` + `ListWorkspace(agentID, relPath)` on a service, jail-checked by cleaning the path and requiring the prefix inside `~/.buddies/workspaces/<agent>/` (symlink/traversal closed before open). Persona docs keep using `GetPromptDocuments`. Both run-card lanes — tasks and plan — derive from `applyEvent` output (task events already carry status/description/result; plan lanes fold the latest `todo_write` tool activity from persisted arguments/results). **Why:** the event stream already reaches the frontend fresh on subscribe+transcript, so adding a query API would duplicate a surface that exists; the only genuinely unreadable data is workspace files, hence the single new reader. **Alternative:** a bound tasks/todo query bus (rejected — unexported registry would need a parallel truth next to the events the transcript must show anyway).

### D9: Picker placement and stickiness
Composer bottom-control rail hosts three controls (agent / model / effort) as popovers on the rail — not caret-token `TriggerMenu`s (those are textarea-bound by design). Sticky defaults use `useLocalPreference` (`buddies.chatDefaultModel` etc.): a *new* session of agent A is created with `sessions.model/effort` seeded from (last-used override for A, else the agent's defaults). **Why:** minimal session-store churn; onclaw's sidebar-derived defaults have no equivalent here and local preference matches the shell's rail-collapse precedent.

## Risks / Trade-offs

- [Runner swap regresses streaming/compaction parity] → phases 1–8 and all record/broadcast mapping stay byte-identical; add a smoke task that runs a turn pre/post swap and diffs the event kinds; the existing suite runs per task batch.
- [Checkpoint gob payloads are eino-internal] → resume only works against the same eino version; upgrades must be paired with a "resume a stored interrupt" test, and `go.mod` eino bumps become change-sensitive.
- [Multi-MB base64 binding calls (20 MB PDFs) stall the UI] → fetch content only on user action (download/preview), chunk by offset if profiling shows jank; upload path is separate and already progress-chip-based.
- [Pending approval with the window closed has no UI] → the run waits safely (spec'd queue behavior); tray/OS notification is a possible follow-up, not a correctness gap.
- [Live vs replay divergence for variants/attachments] → both feed the same reducer from the same event payloads; test matrix explicitly covers load-after-live for each new payload.
- [Stale bindings break the frontend after Go changes] → every Go signature task carries a `wails3 generate bindings` step plus a `task build` verification (known repo gotcha: bindings silently stale otherwise).
- [Busy session stuck if resume fails] → resolve errors leave the pending state intact (conflict-safe) and cancel-during-pending always clears; no path leaves busy without a terminal or pending marker.

## Migration Plan

All schema changes are additive forward migrations: `000008` (sessions `model`/`effort` TEXT DEFAULT '', agents `effort` TEXT DEFAULT ''), `000009` (attachments table); new event kinds (`turn_cancelled`, `approval_required`, `approval_resolved`) ride the TEXT kind column and are skipped by any older replay path. Rollout order = wave order in tasks.md (foundation → runtime → surfaces), because each wave is independently shippable: an intermediate build with only 000008 applied still runs (pickers fall back to agent defaults). Rollback strategy is binary-level only (forward migrations are not reversed — additive columns/tables are inert to a reverted binary). `checkpoint_*` (compaction) and `adk_*` (interrupt) key prefixes share the existing checkpoints table without collision.

## Open Questions

- Effort budget tier values (claude 4k/16k/32k; gemini 512/2048/8192) are initial guesses — tune against real latency/output without touching specs (they are capability *options*, not values).
- Whether the run card's plan lane should also offer a bound `.todo.json` reader for sessions selected mid-run: derivable from events already, so the reader is optional polish, not contract.
- Tray-level notification for approvals pending while the window is hidden (would be its own later change; current specs only cover in-transcript behavior).

# Design

## Context

The standalone webhook pipeline (add-workspace-webhooks) delivers end to end, but channel-target runs are invisible in the UI. Three verified facts pin the design: (1) the channel room renders a session transcript it binds client-side, and the human-only session index deliberately excludes unattended origins (`internal/agents/runner.go` `indexAgentSession`); (2) the run's final-text reply posts through the chokepoint (`PostFromAgent`) onto the channel's message feed — the same surface summon auto-posts (fanout D9.1) and gateway posts ride — whose store slice had no renderer and whose REST loader and live SSE subscription had no caller; (3) webhook run transcripts persist under synthetic ids (`whstandalone_<webhook>_<ts>`, mirroring the connection lane's `whconn_` shape) that no discovery surface enumerates. The delivery log is the one durable, queryable record tying runs to endpoints.

The first cut of this change built a dedicated room strip over a per-channel listing API; live use rejected it (an activity log table is not conversation, and expanded-by-default it displaced the transcript) and the user then redirected: the strip goes, and the channel must simply work when a webhook comes — the reply belongs in the room, as the agent's message.

## Goals / Non-Goals

Goals: a webhook-delivered reply is visible in the channel room — rendered as the invoked agent's message among the channel's other messages, on open and live; an admin can compare webhook runs with scheduled ones on the run history screen and open their transcripts — without violating the human-only session index, changing service attribution/gating, or adding a second write path.

Non-Goals: merging run transcripts inline into the session transcript (the reply is delivered as a message; the full run transcript opens from the run history); re-pointing webhook runs at channel sessions (the room's session is client-minted per browser — not server-addressable — and the runner's compose guard keeps unattended origins off channel coordinates); live run-status broadcasting into the room (v1 delivers the reply, not the in-flight state); connection-webhook lane delivery (same shape, follow-up); scheduler channel-delivery telemetry display beyond the feed itself.

## Decisions

- **D1 — No run-path changes; the delivery log is the anchor.** Anchoring runs into channel work sessions was evaluated and rejected: the runner's documented contract is that unattended origins never carry channel coordinates (`internal/agents/runner.go` compose guard — "scheduler and heartbeat runs never carry ChannelID, but a malformed request must not compose channel docs into an unattended profile"), and `ChannelID`/`WorkSessionID` non-empty activate channel-docs composition, channel-tool wiring, and work-session plumbing regardless of origin. Silently changing run grounding for visibility would trade a real behavior regression for a cosmetic one. The delivery-log row already ties every run to its endpoint, and the endpoint to its channel — that join is the anchor. Minting work sessions from the webhook path was rejected for the same class of reason: sessions require a root message and carry watchdog/human-gate lifecycle the webhook path must not trigger.
- **D2 — Run telemetry rides the submitted log row; the submitter always drains.** Run telemetry (status running → completed/failed/cancelled, duration, tokens) rides three columns on the delivery-log row — a submitted delivery is 1:1 with its run, mirroring how SchedulerLastRun doubles on the scheduler — rather than a second runs table forking the record. The submitter drains every run's event tap on a detached goroutine (the tap is best-effort with drop-new semantics; today channel targets drain it and thread targets drop it, so an unconditional drain changes no run behavior), derives status/tokens/duration with the scheduler drain's exact semantics (last usage frame is the total; TurnCompleted/Error/Cancelled; tap ended without a terminal event = completed, the fanout's success-by-default), posts the channel final text as before, then finishes the row best-effort — a telemetry write failure never surfaces to the delivery ack.
- **D3 — The room renders the channel's message feed; no webhook-specific surface.** The per-channel listing API and the room activity strip were built, shipped, and then removed by live-pass verdict: a delivery log rendered as UI reads as a log table, not conversation, and the reply already has a home — the channel's message feed, where the drain's `PostFromAgent` post has landed all along and where summon auto-posts and gateway posts ride. The room now loads that feed with its history on open (`loadChannelFeed`), subscribes to the channel's live event stream while open (`streamChannelEvents` folding through `applyChannelEvent`), and renders feed entries as conversation messages (agent rows as the invoked agent's message). The deferred "messages-feed rendering decision" is thereby made: the feed is the room's delivery surface for every unattended origin at once.
- **D4 — Session ids stay synthetic and unindexed.** Registering a `wh_` binding prefix or indexing webhook sessions would put unattended conversations into per-user sidebars — the exact contract runner.go records against. Discoverability comes from the room feed (D3) and the workspace run history (D5).
- **D5 — The workspace-wide run feed rides the webhooks pane's trust tier.** `GET /workspaces/:slug/webhook-runs` (integrations.write — the same tier as every webhooks pane route; the feed exposes endpoint names and event shapes) returns the workspace's submitted deliveries projected with endpoint name, bound agent (name resolved at read time), status, duration, tokens, newest first, bounded. The run history screen merges it beside the scheduler feed best-effort: a member without integrations write sees scheduled runs only, never an error. Rejected/filtered/duplicate deliveries are not runs and stay in the delivery log.

## Risks / Trade-offs

- [Delivery log as the only run record] → pruned to the newest 100 per endpoint; the run-history feed inherits that bound by design ("bounded like the per-endpoint log").
- [Room feed adds a load + a subscription per room open] → one bounded history read and one SSE stream per open channel room, gated by ChannelsRead; the same posture the agent-chat live attach already holds.
- [Feed entries lack roster-resolved user names today] → agent rows (the webhook case) resolve names from the workspace roster; other-user rows render with the generic member label until the roster wiring lands.

## Migration Plan

Purely additive on top of the shipped pipeline: room feed load/subscribe/render, one store query, one route, one drain generalization, three log columns (000076, defaults backfilling legacy rows as blank → read as completed), and the run-history merge. The removed strip and listing chain revert cleanly (the feed rendering supersedes them). Rollback = revert the room feed wiring and the run-history merge; the telemetry columns are inert.

## Open Questions

None blocking. v1 bounds the run-history feed at the screen's page size and renders feed replies without run summaries.
